# Codeyoung trial class booking

A Next.js app (React frontend and Node.js API routes in one project) backed by Postgres. Parents book a one-hour trial class, a mentor is assigned automatically, and both receive a confirmation with a class link. Everyone sees times in their own time zone.

There are three audiences, each with its own pages:

| Who | Where | What they do |
| --- | --- | --- |
| Parent | `/book`, `/booking/<token>` | Pick a time, get a confirmation page, view or cancel from the link in the email |
| Mentor | `/mentor` | Sign in, see today's and upcoming classes in their own time zone, with the parent's local time and the join link |
| Admin | `/admin` | Overview and capacity, all bookings (search, filter, cancel), manage mentors (add, edit shift, deactivate, reset access code), email log |

## Run it

Requires Node.js 20.6 or later (22 recommended) and a Postgres database (Neon works).

```bash
npm install
cp .env.example .env     # then fill it in, see below
npm run db:setup         # creates tables, seeds 10 mentors, prints their access codes once
npm run dev              # http://localhost:3000
```

Other commands: `npm test` (unit tests, no database needed), `npm run typecheck`, `npm run build && npm start`.

### Environment (`.env`)

| Variable | Required | Purpose |
| --- | --- | --- |
| `DATABASE_URI` | yes | Postgres connection string. `.env` is git-ignored; never commit it |
| `SESSION_SECRET` | production | Signs login cookies. Generate with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |
| `ADMIN_PASSWORD` | yes for `/admin` | Admin login is disabled while this is empty |
| `APP_URL` | recommended | Base URL for the manage link in emails (default `http://localhost:3000`) |
| `ADMIN_TIMEZONE` | no | Zone the admin portal shows times in (default `Asia/Kolkata`) |
| `SMTP_URL`, `EMAIL_FROM` | no | Real email delivery. Without `SMTP_URL`, emails are only recorded (see Emails below) |

### Signing in

- **Admin:** `/admin`, password from `ADMIN_PASSWORD`.
- **Mentor:** `/mentor`, the mentor's email plus the access code printed by `npm run db:seed`. Seed emails look like `ananya@mentors.codeyoung.example`. An admin can reset any code from Admin > Mentors; the new code is shown once.

### Speed

Use the production build for real speed: `npm run build && npm start`. `npm run dev` compiles each page the first time you open it, so it is always slower.

- Navigation is client-side (`next/link`), with links prefetched and visited pages cached in the browser for 30 seconds. Each portal shows a loading skeleton at once while data arrives.
- The server opens its database connections at startup, keeps them for 10 minutes, and pings the database every 4 minutes so a serverless Postgres doesn't suspend. This removes the 0.7s cost of a cold connection.
- Queries on each page run in parallel, and the booking page caches days it has already loaded.

## Requirements and how they are met

1. **Different time zones, local times always shown.** Every instant is stored as UTC (`timestamptz`). Each person has an IANA zone name (`America/New_York`), never a fixed offset. Parents see their own zone on the booking page, the confirmation page and the email. Mentors see their zone in the portal and the email. Each email also gives the other party's local time. Zone abbreviations are pinned to one locale (and India shows `IST`), so output doesn't depend on the viewer's machine settings.
2. **Daylight saving.** A parent's day is generated by stepping one real hour at a time from local midnight to the next local midnight, giving 23 slots on spring-forward days and 25 on fall-back days. Mentor shifts are wall-clock hours in the mentor's zone, so a mentor in a DST zone keeps the same local shift when clocks change. The booking page warns when the chosen date has a different offset from today. The US and UK change on different dates; tests cover both, plus a New York mentor across the change.
3. **Dummy link.** Each booking gets `https://meet.codeyoung.example/trial/<id>`, shown on the confirmation page, in both emails and in the mentor portal.
4. **At most 2 classes per mentor per day**, counted on the mentor's local calendar day (the day they actually work; a US evening is often the next date in India). Enforced in the scheduler under a lock, with tests.
5. **No mentor available.** Full hours are shown crossed out. If a day has nothing open the page says why (too soon, too far, nobody on shift, fully booked) and offers the nearest open times. If a slot fills while the parent is booking, the API returns `409 NO_MENTOR_AVAILABLE` with three alternatives. If nothing is free for 30 days, it says so and points to support.

## Design decisions

**Concurrency.** `POST /api/bookings` runs in one transaction that first takes a Postgres advisory lock, then loads mentors and confirmed bookings, decides, and inserts. Concurrent requests therefore run one at a time, even across several server instances. A partial unique index on `(mentor_id, start_utc) where status = 'confirmed'` is a second line of defence. Verified by firing 10 simultaneous requests at an hour with 5 mentors on shift: exactly 5 succeeded, each with a different mentor.

**Scheduling is pure.** `lib/scheduling.ts` takes arrays in and returns results, with no database access, so it is fast to unit test. `lib/booking-service.ts` wraps it in the transaction. Only confirmed bookings are loaded, so cancelling frees the slot and the daily cap immediately.

**Mentor assignment.** Among free mentors, the one with the fewest classes that day, then fewest overall, then by id. Seed data has 5 mentors on an early-morning IST shift (US evenings) and 5 on an evening IST shift (UK afternoons and evenings).

**Rules** (all in `lib/config.ts`): 1-hour classes, book at least 2 hours ahead and at most 30 days ahead, one upcoming trial per parent, parents can cancel online until 60 minutes before the start (admins can cancel any time before the end).

**One trial per parent** is keyed on a normalised email: case, `+tags` and Gmail dots are ignored, so `a.b+x@gmail.com` and `ab@gmail.com` count as the same parent.

**Cancellation and rescheduling.** The parent's link (`/booking/<token>`, 24 random bytes) lets them cancel, then book a new time. Admins can cancel from Bookings. Both sides are emailed.

**Security.**
- Admin uses a password; mentors use per-mentor access codes stored as scrypt hashes. Sessions are HMAC-signed, expiring (8h), `httpOnly`, `sameSite=lax` cookies, `secure` in production.
- Every admin page and server action re-checks the session; mentor pages re-check the mentor against the database, so deactivation takes effect immediately.
- Login attempts and booking requests are rate limited per IP (and per email for mentor login). The limiter is in memory, so it is per instance; move it to Redis or the database if you run several.
- There is no public endpoint that lists bookings. Parent emails are visible only to admins, and each mentor sees only their own classes.
- Inputs are length-limited and control characters are stripped before they reach emails or logs.

**Emails.** Every email is written to the `email_log` table (viewable in Admin > Emails) and, if `SMTP_URL` is set, sent through Nodemailer. A mail failure never undoes a booking; it is logged as `failed`.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/slots?date=YYYY-MM-DD&tz=<IANA zone>` | Hourly slots for that calendar day in the parent's zone, each `open`, `full` or `closed` (with a reason), plus `nextAvailable` when the day has nothing open |
| POST | `/api/bookings` | Body `{ parentName, parentEmail, timezone, startUtc }`. Returns `manageUrl`, the booking time and the mentor's name and zone |

Errors use `{ error: { code, message, suggestions[] } }`, where `suggestions` are UTC start times of the nearest open slots.

## Project layout

```
app/page.tsx                 landing page
app/book/                    parent booking flow (client component)
app/booking/[token]/         parent confirmation, view and cancel
app/mentor/                  mentor login and dashboard
app/admin/                   admin login, overview, bookings, mentors, emails
app/api/                     slots and bookings endpoints

lib/repo.ts, lib/db.ts       Postgres access
lib/auth.ts, session-token.ts, password.ts, rate-limit.ts
lib/notify.ts                email content, delivery and logging
db/schema.sql                tables and indexes (idempotent)
scripts/                     db:migrate and db:seed
tests/                       Vitest tests, including DST transition dates
```

## Known limitations

- Two dependency advisories remain (in Next.js 14 and its bundled PostCSS). The fix is a major upgrade to Next 16, which is a separate migration.
- A mentor has one shift per day, and it cannot cross midnight (the evening seed shift ends at 24:00).
- Parents have no account; the emailed link is their credential.
- Calendar invites (`.ics`) are not generated.
