# Codeyoung trial class booking

A Next.js app (React frontend and Node.js API routes in one project) where parents book a one-hour trial class, a mentor is assigned automatically, and both receive a confirmation with a class link. Each confirmation shows the time in that person's own time zone.

## Run it

Requires Node.js 18.18 or later.

```bash
npm install
npm run dev        # http://localhost:3000
npm test           # scheduling and DST tests
```

Production build: `npm run build && npm start`.

Confirmation emails are a dummy transport. They are printed to the server console, and the booking page also shows them after a booking.

## Pages

- `/` is a single landing section with a live clock showing your local time next to India time.
- `/book` is the booking flow. Pick a time zone (detected from the browser), a date, and an hour. Enter a name and email, then book.

## API

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/slots?date=YYYY-MM-DD&tz=<IANA zone>` | Hourly slots for that calendar day in the parent's zone, each marked `open`, `full` or `closed` |
| POST | `/api/bookings` | Body `{ parentName, parentEmail, timezone, startUtc }`. Returns the booking, the mentor and the email previews |
| GET | `/api/bookings` | Lists all bookings (for reviewers) |

Errors use the shape `{ error: { code, message, suggestions[] } }`, where `suggestions` are UTC start times of the nearest open slots.

## Design decisions

**Time storage.** Every instant is stored in UTC. People are stored with an IANA zone name (`America/New_York`), never a fixed offset, so DST rules come from the tz database rather than from hand-written logic. Conversion to local time happens only for display, in the browser and in the emails.

**Daylight saving.** A parent's day is generated by stepping one real hour at a time from local midnight to the next local midnight. That gives 23 slots on spring-forward days and 25 on fall-back days, and the duplicate 1 AM on fall-back is labelled with its zone abbreviation (EDT and EST). The booking page warns when the chosen date is on a different offset from today, or when the clocks change on that date. The US and UK change clocks on different dates and India never does, and the tests cover both.

**Whose "day" for the 2-classes cap.** The brief doesn't say, so the cap counts the mentor's local calendar day. That is the day the mentor actually works. A US evening often falls on the next date in India, and the tests cover this case.

**Mentor assignment.** Each mentor has working hours in their own zone. The seed data has five mentors on an early-morning IST shift that overlaps US evenings, and five on an evening IST shift that overlaps UK afternoons. Among the free mentors, the one with the fewest classes that day is picked, which spreads load evenly.

**No mentor available.** Capacity is exactly 20 classes a day (10 mentors × 2), so this case will happen. Full slots are shown crossed out instead of hidden. If a booking fails because a slot filled up in the meantime, the API returns `409 NO_MENTOR_AVAILABLE` with the three nearest open times, which the page offers as one-click alternatives.

**Other rules.** Bookings must be at least 2 hours ahead and at most 30 days ahead. Each parent email can hold one upcoming trial. All of these limits are in `lib/config.ts`.

**Concurrency.** `createBooking` is synchronous, so in a single Node process the check-and-insert cannot interleave and two parents cannot take the same last mentor. With a real database, this should run in a transaction with a unique constraint on (mentor, start time).

## Project layout

```
app/page.tsx            landing page
app/book/page.tsx       booking flow (client component)
app/api/slots           availability endpoint
app/api/bookings        booking endpoint
lib/scheduling.ts       all scheduling rules (pure functions, unit-tested)
lib/notify.ts           confirmation emails (dummy transport)
lib/mentors.ts          seed data for the 10 mentors
lib/store.ts            in-memory store
tests/                  Vitest tests, including DST transition dates
```

## Limitations and next steps

- The store is in memory, so bookings reset on restart. SQLite with Prisma would be the next step.
- Emails are logged rather than sent. Nodemailer pointed at Ethereal would give real previewable emails.
- There is no mentor-facing view yet. A `/mentor/:id` page listing classes in the mentor's zone would reuse `formatInZone`.
- Calendar invites (`.ics`) would let both sides add the class with the time zone embedded.
